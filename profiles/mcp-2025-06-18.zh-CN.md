# MCP profile：2025-06-18

本 profile 适用于明确选择 MCP revision `2025-06-18` 的 implementation。它提供 historical compatibility guidance，不建议新 server 默认采用这一 revision。

## Normative sources

- [Specification index](https://modelcontextprotocol.io/specification/2025-06-18)
- [Key changes from 2025-03-26](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- [Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)
- [Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)
- [Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

Normative `MUST`、`SHOULD`、`MAY` 的含义来自 specification，而不是本摘要。

## Protocol shape

- Connection 存在 lifecycle：普通操作之前先通过 `initialize` negotiation；初始化成功后，client 发送 `notifications/initialized`。
- Streamable HTTP 使用一个同时支持 POST 与 GET 的 MCP endpoint。Request 可以收到单个 JSON object 或 request-scoped SSE stream。
- Server 可以在 initialization 时用 `Mcp-Session-Id` 建立真实 transport session。若没有拥有 session state 与 expiry semantics，就不应发出装饰性或恒定不变的 session identifier。
- 后续 HTTP requests 通过 `MCP-Protocol-Version` 携带 negotiated revision；invalid 或 unsupported value 是 HTTP error。
- 即使基础 JSON-RPC 2.0 定义了 batches，本 MCP revision 也不支持 JSON-RPC batching。
- Structured tool output、tool result 中的 resource links、elicitation、OAuth protected-resource metadata 与 Resource Indicators 都属于本 revision 的变化面。

## Streamable HTTP obligations

在 MCP endpoint：

- 验证 incoming connections 的 `Origin`；local server 除非明确需要更广 reachability，否则只 bind loopback；
- POST body 必须是单个 JSON-RPC request、notification 或 response，不能是 batch；
- 接受 notification 或 response 后返回无 body 的 `202 Accepted`；
- JSON-RPC request 的响应使用 `application/json` 或 `text/event-stream`；
- 若未实现 GET streaming，返回 `405 Method Not Allowed`，不要伪装 SSE；
- 把 `Mcp-Session-Id`、SSE resumability 与 server-to-client messaging 当作带真实 state obligations 的 optional features，而不是 compatibility decorations。

这些 protocol rules 不能代替 HTTP framing limits、authentication、admission control 或 deployment policy。

## Implementation consequences

1. 显式建模 lifecycle state，使实现能按 declared revision 拒绝 pre-initialization call 与 invalid re-initialization。
2. Stateless implementation 要保持诚实：不发 `Mcp-Session-Id`、不声称 resumability、不需要 stream 时就返回普通 JSON。
3. Dispatch 前先分类 message kind。Notification 可以被接受且不返回 JSON-RPC response，但“接受 notification”不等于“任意 notification 都可执行 side effect”。
4. 所有 transports 共用 capability validation。Convenience REST route 不能绕过 tool allowlist、argument schema 或 resource budgets。
5. 把 negotiated `protocolVersion`、server capabilities 与 tool metadata 当作由 tests 约束的 runtime contracts。

## Revision-bound test obligations

- `initialize` 只对 supported version 成功，并返回真实 capabilities。
- Initialization 前的普通调用依 lifecycle contract 被拒绝。
- `notifications/initialized` 被识别为 notification，且不会收到 JSON-RPC result。
- 即使 generic JSON-RPC library 接受 batch-shaped JSON，本实现也会拒绝。
- 若发出 `Mcp-Session-Id`，它必须 unique、opaque，后续 request 会验证，可 expiry、可 termination；否则断言该 header 缺席。
- POST notification/response 被接受时返回无 body 的 HTTP 202。
- Unsupported `MCP-Protocol-Version` 被拒绝。
- 在真实 socket boundary 覆盖 Origin、content type、body size、incomplete-body deadline 与 request-target tests。

## Migration boundary to 2025-11-25

Lifecycle 与 optional session model 保持不变。后续 revision 新增或明确多项内容，包括 present invalid `Origin` 返回 HTTP 403、polling-style SSE、URL-mode elicitation、sampling 中的 tool-calling、Client ID Metadata Documents 与 experimental tasks。不能只改 version constant 就把这些 requirements 反向套进来。

## Migration boundary to 2026-07-28

这是 breaking architecture change，不是小 schema bump。后续 revision 删除 protocol-level sessions 与 initialize handshake，让每个 request self-describing，删除 server-initiated JSON-RPC requests，加入 `server/discover`、required HTTP routing headers，并改变 streaming/cancellation semantics。应使用 [2026-07-28 profile](mcp-2026-07-28.zh-CN.md) 并重写 lifecycle tests，而不是强迫两个时代共用一个 state machine。

## Known unknowns

- Host products 可能只实现这项 historical revision 的一个 subset。
- SDK defaults 与 compatibility shims 不能证明 wire-level behavior。
- Authorization requirements 取决于 server 是否 remote、谁拥有 resource server、哪个 issuer 是 authority。
- 对 deployed endpoint 的任何结论，在实际 proxy、TLS、authentication 与 host path 上测试前都仍是未验证。
